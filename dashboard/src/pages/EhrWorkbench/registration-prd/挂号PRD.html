合并模块：03-产品范围与边界

门诊挂号登记产品范围与边界

1. 产品定位与目标

门诊挂号登记是门诊业务链的入口：识别或建立患者身份 → 分配号源 → 收取挂号费 → 生成就诊记录（visitCode）。它是 AMB_REGIST.CHARGE_LOCK（挂号收费锁）与 visitCode（就诊流水号）的发源地——门诊收费、医生站、药房全部挂在这条流水上（证据：prd-doc 一章；AmbRegistMapper.xml 两侧同源）。

主链：查询排班号表 → 选号（锁号源）→ 读卡/建卡定位患者 → 费别/身份/优惠确认 → 算费（挂号费+卡费+病历本）→ 挂号收费弹窗（支付/发票）→ 窗口挂号事务落库 → 打印指引单 →（分诊台）分诊/报到 → 接诊。

产品目标（可验收）：

  1. 身份正确：五种介质（就诊卡/身份证/医保卡/电子凭证/手工）识别收敛到唯一患者主索引，多命中不自动猜测。
  2. 号源不超：并发挂号不超过排班容量；选择态计数与可挂容量分离（BR-01）。
  3. 流水唯一：visitCode 全院唯一、原子分配；chargeLock 互斥语义统一（BR-02/BR-03）。
  4. 结果原子：窗口挂号"挂号+收费+票据+分诊"一次事务，中断无半程数据（BR-10）。
  5. 旧功能全量盘点：F-001～F-056 全部有唯一映射、目标处置、证据状态和验收责任人；003 独有项未经确认不得标成已继承。

  5. 预约：F-037～F-039（预约挂号/取消、预约取号、预约管理）。

  • 挂号费收费与日结本体——收费事务、日结缴款归《门诊收费》包；本包只负责锁号联动（chargeLock/BR-03）、费用锁定前的算费校验与窗口挂号事务内嵌的收费明细/收据写入（020 windowRegist 同事务范围）。

门诊挂号登记产品 PRD

0. 产品演进原则

本产品基于旧产品演进，不是绿地重建。020（潼南，client-pat，PatadAmbRegistView 三 Tab + 2567 行 Controller）是目标院区的默认事实基线；003（东港，HIP-CLIENT-PATAD，PatadAmbRegistView 双 Tab + RegistCommand 789 行）只作补充证据。任何 003 独有行为须经业务确认，版本冲突按 020 处理。所有需求标记为：

  • 兼容项：保持旧产品结果和责任边界。
  • 优化项：不改变结果，只改善操作、提示、可见性和恢复能力。
  • 补齐项：针对旧产品断点增加服务端校验、并发保护、审计或配置能力。

F_ID 沿用 registry 登记编号（F-001～F-036）并向后扩展（F-037～F-056），不自造第二套编号；测试、Legacy 证据和跨域追踪只维护一套编号。挂号登记与门诊收费共用 chargeLock/visitCode 状态语义，不自创第二套状态机。

1. 问题陈述

挂号窗口需要同时处理五通道身份识别、号源并发、费别分流、临床限制、发票与支付校验、窗口事务落库、chargeLock 联动、退号多重校验和预约/取号/分诊。两个现有项目已经承载这些业务，但实现分散且语义不一致：003 选号阶段用客户端 GET/PUT 读改写号额（无原子性）、挂号 Tab 权限来源不明、急诊线独立成页；020 用服务端条件扣减但双路径并存、取消预约命令空实现、取号提交链被注释。产品要在保持业务连续性的前提下，统一挂号工作台、补齐服务端原子占号与服务端重校验，并处理 003/020 在号别体系、锁号时机、预约放号、退号规则和票据归属上的差异（全部进差异表）。

2. 目标

  • 让挂号员在一个连续工作台中完成从读卡定位到打印指引单的窗口挂号流程。
  • 提交前明确展示号源余量、临床限制结论、发票余量与应缴金额。
  • 号源并发、visitCode 分配、窗口事务失败均有服务端保证与恢复路径。
  • 兼容不同院区的费别分流、退号口令、减免与必填参数策略（参数化，不硬编码）。
  • 挂号完成后 chargeLock/visitCode 可靠供收费、医生站、分诊消费。

  • 分层：页面 → HTTP 适配 → 应用服务（挂号/患者/排班/预约/分诊）→ 领域对象（RegistRecord/VisitEncounter/ScheduleSlot/TriageSeat）→ 端口（ChargeLock/Insurance/Integration/Print）→ 外部系统。

  • 所有状态校验、数量校验、资格校验、权限校验在服务端执行；前端只做预检与提示。
  • 金额统一两位小数、按 Econ_Rounded 舍入；禁止浮点直接求和；减免金额服务端计算。
  • 禁止在 Command/Service 中散落读取配置键；统一经参数服务初始化（04 章 15 节）；同名键跨现场语义不等价，禁止按名字假设。
  • 跨系统写操作（JH0105/医保/电子发票）必须有幂等键 + UNKNOWN 落库 + 查询恢复路径；不允许"失败即重试"。
  • 序号分配必须有（排班ID+序号）唯一约束兜底；003 无 order by 的 listByScheduleId 查询模式禁止照搬。
  • 技术可靠性机制（Outbox、重试表、消费去重）属于基础设施，不作为挂号领域业务方法建模。

4. 关键状态原则

  1. 挂号状态（NO_CLINIC/CLINIC/BACK_REGIST）只能由业务事件（挂号提交、接诊、退号）驱动，禁止人工直接改状态。

  3. chargeLock 谁加锁谁解锁，统一为服务端收费事务语义；020 客户端 dispose 解锁为旧语义，废弃（BR-03，Q-05 关联）。
  4. visitCode 与挂号 ID 由 Oracle 序列（AMB_VISIT_CODE_ID / AMB_REGIS_ID）原子分配，分配后不可复用（BR-02）。
  5. 退号到达阈值（patad_CancelRegistNum，默认 3）时 examine 阻止再次挂号，与三日重复共用验重入口（BR-04）。
  6. 停诊排班不可挂号；停诊处理已挂号患者走改约或全额退号（spec 分支）。

1. 号源与流水

  • BR-01 号源不可超挂：挂号提交以服务端原子条件扣减为准（UPDATE ... SET REG_REMAINING_NUM=REG_REMAINING_NUM-1 WHERE ID=? AND REG_REMAINING_NUM>0，020 AmbSchedulingRegMapper.xml:962-966）；页面选择态计数（003 ±1）不是容量；扣减同时校验排班 ACTIVE/停诊/日期；号源为 0 提示「已无号源！」。（F-001/F-015/F-043，不可配置）
  • BR-02 visitCode 原子唯一：visitCode 由序列 AMB_VISIT_CODE_ID 原子分配（003 Mapper :2030 / 020 Mapper :1076-1079）；GET visitCode 支持 lockUser 锁定；全院唯一、不复用。（F-041，不可配置）
  • BR-03 chargeLock 互斥：update AMB_REGIST set CHARGE_LOCK=? where VISIT_CODE=?（两项目 SQL 一致）；收费事务开启加锁、结束（含异常）服务端解锁；锁定期间挂号侧患者数据变更被拒；废弃 020 客户端 dispose 解锁。（F-042，不可配置；Q-05 关联）

2. 验重与临床

  • BR-04 重复挂号验重：提交前逐号别 POST Regist/examine；当日同患者同号别有挂号（003 数 BACK_REGIST 达 3 次阻止；020 patad_CancelRegistNum 默认 3 可院区覆盖）或三日重复时按配置确认/阻止；确认继续须留痕。（F-044/F-055，可配置 patad_CancelRegistNum）

  • BR-08 发票强校验：当前人员门诊收据余量 endNo + 1 - nowNo 不少于所选号别数，否则「此人当前结算发票剩余N张，不足以结算当前挂号，请先领取发票」；无发票「此人没有结算发票.先去领取发票」；无支付方式「没有支付方式，找管理员配置支付方式」。（F-040/F-056，可配置 Econ_Use_Amb_Invoice）

6. 通用

  • BR-13 权限与口令：挂号 Tab 是权限功能（getCanRegist，赋值来源 Q-04）；退号口令按 Patad_CancelRegist；分诊台动作受 TriagePermRelation 号别权限约束。（F-010/F-025/F-031，可配置）

6. 一致性与幂等要求

  • 本地事务：挂号+号额+坑位+分诊+收费明细/收据同事务（020 @Transactional 基线）；跨系统（仅对已经确认启用的 JH0105、医保、电子发票）走"先落事实 → 调外部 → 按结果落库"。
  • 幂等：requestId（提交）、挂号引用（退号/推送）、VISIT_CODE（chargeLock）全链路透传。
  • 序列原子：AMB_REGIS_ID/AMB_VISIT_CODE_ID 数据库序列分配；序号加（排班ID+序号）唯一约束兜底。
  • UNKNOWN 收敛：已启用的 JH0105、反结算、电子发票未知状态必须有补偿任务收敛，不允许长期悬挂。

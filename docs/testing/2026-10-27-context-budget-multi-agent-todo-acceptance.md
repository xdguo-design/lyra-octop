## 一、范围与当前真实状态

本文件同时覆盖两个相互关联但成熟度不同的功能：

| 模块 | 当前可测能力 | 当前**不可当作已完成**的能力 |
|---|---|---|
| 上下文 P1 | `context_budget.py` 纯函数预算、来源与上限校验；8 个已有单元测试 | 真实模型调用前自动组装/注入上下文、影子模式监测日志、压缩/恢复、上下文检查面板 |
| 单 Agent Todo | Agent `write_todos` 输出的清单展示、编辑、增删改排、同步给 Agent | 仅前端勾选不等于执行完成；不能从聊天回复断言任务已通过验收 |
| 团队 Todo | 按团队成员展示清单归属；通过主 Agent/目标路由向对应成员转交；旧草稿冲突保护 | 统一的团队任务数据库、依赖调度、可靠任务领取、全链路 Run 证据校验尚未开发 |

**测试判定原则：** 未实现功能记录 `N/A（尚未开发）`，不能判 `PASS`；运行时集成未验证记为 `BLOCKED` 或 `FAIL`，不能以单元测试通过替代端到端验收。

## 二、环境准备与统一约束

1. 在独立测试机或测试实例拉取 `dev`，确认工作区无未提交改动；不要在生产环境运行写入或冲突测试。
2. 准备两个可正常聊天的个人 Agent（A、B）、一个包含 A/B 的团队 Agent（Host），另准备测试用户 U1。权限隔离用例需要第二个测试用户 U2。
3. 每个 Agent 绑定可用模型；准备**不含任何真实密钥、病历、客户隐私**的测试项目与虚拟任务。
4. 保留浏览器开发者工具、Octop 服务日志、与请求关联的 `thread_id`、Agent ID、Run ID（如存在）、截图和 Git 版本。
5. 对于“真实成员执行”用例，确认 Agent 确实调用 `write_todos`、`ask_agent` 等工具；若模型未主动调用工具，可使用测试提示词重新触发，不能伪造通过记录。
6. 测试期间**不**修改生产权限、共享真实密钥、不合并 `main`。

## 三、上下文 P1：自动化测试用例（P0 门禁）

### CTX-01：模型窗口与输出预留（P0）
- **准备：** 无需接入真实模型。
- **动作：** `resolve_context_budget(model_context_tokens=64000, configured_input_cap_tokens=60000, output_reserve_tokens=4000, safety_margin_tokens=1000)`。
- **期望：** `effective_input_cap_tokens=59000`，`source=model_profile`，`is_estimated=False`。
- **证据：** 单元测试日志 + 被测 Git SHA。

### CTX-02：Agent 配置输入上限优先（P0）
- **动作：** 模型 128000、Agent 上限 20000、输出预留 4000、安全预留 1000。
- **期望：** 最终输入上限 `20000`，不能超过 Agent 限制。

### CTX-03：模型窗口未知（P0）
- **动作：** 模型窗口 `None`，fallback=24000、输出预留 2000、安全预留 500。
- **期望：** 最终上限 `21500`、`is_estimated=True`；**不得**无提示当作真实模型窗口。

### CTX-04：非法模型窗口（P0）
- **动作：** 输入布尔值 `True` 作为模型窗口，fallback=16000。
- **期望：** 忽略非法值，使用 fallback 并标记估算状态。

### CTX-05：上下文来源与 Token 总数（P0）
- **动作：** 传入两条来源清楚的 `ContextItem`，估计 120 与 80 tokens。
- **期望：** 校验通过，总估算 `200`；每条包含 `source_id`、`scope`、`trust_level`、`sensitivity`、`inclusion_reason`。

### CTX-06：无作用域或缺纳入理由（P0）
- **动作：** `scope=" "` 或 `inclusion_reason=" "`。
- **期望：** 校验失败、返回具体字段错误；不能悄悄接收。

### CTX-07：负 Token / 超量条目（P0）
- **动作：** `estimated_tokens=-1`；另调用 `validate_context_items([item], max_items=0)`。
- **期望：** 均失败，不造成进程异常或无限扩展。

### CTX-08：非结构化输入（P0）
- **动作：** `validate_context_items([{"source_id":"raw"}])`。
- **期望：** 返回无效和结构类型错误，不崩溃。

### CTX-09：静态校验与兼容性（P0）
- **动作：** 运行上述 `pytest`、`ruff`、`mypy` 三个命令。
- **期望：** 三个命令均成功退出；若失败记录错误日志和触发版本。

### CTX-10：影子模式真实调用统计（后续 P1，当前 N/A）
- **动作（未来）：** 使用 32k/128k 不同模型重复同一组多轮任务，采集调用前估算与 Provider 实际输入 Token。
- **期望（未来）：** 有真实来源 ID、纳入/省略理由、预算、实际/估算偏差和压缩事件，不改变模型原始输入。

## 四、Todo 与 Agent 双向交互：人工测试（P0）

以下步骤要求在**测试环境**进行。每个用例记录实际 Agent ID、会话 ID、截图与运行/工具证据。

### TODO-01：单 Agent 自动生成清单
- **操作：** 新建 A 会话，输入：“请将‘检查 API、修改功能、编写测试、回归验证’拆为 Todo，并使用 write_todos 维护进度。”
- **期望：** 对话出现实际工具产生的任务清单，顺序和数量合理；未执行步骤不是“已完成”。
- **失败判定：** 只有普通文本没有实际 Todo 工具输出，不应当作工具交互通过。

### TODO-02：单 Agent 页面编辑后回传
- **操作：** 打开 Todo 编辑，修改第二项、增加“检查异常场景”、改变顺序，点击“同步给 Agent”。
- **期望：** 发送出的消息包含清单最新顺序和状态；A 接收到修改，使用自身 `write_todos` 更新；无重复、无丢失。
- **证据：** 编辑前/后截图、发送消息、工具轨迹。

### TODO-03：取消编辑
- **操作：** 修改清单但点“取消”，再打开编辑。
- **期望：** 放弃本地修改，清单仍为原始 Agent 状态。

### TODO-04：执行期间的编辑与同步限制
- **操作：** A 正在响应时打开清单编辑、尝试同步。
- **期望：** 可编辑草稿但同步按钮禁用，提示“Agent 执行中”，不能创建并行冲突发送。

### TODO-05：过期草稿冲突
- **操作：** 编辑已有清单期间，让同一清单的 Agent 源数据发生变更（可通过受控测试模拟/触发），再尝试同步。
- **期望：** 提示任务清单已更新，同步禁用；取消并重新编辑后看到最新状态，不覆盖新进度。
- **备注：** 若测试环境无法稳定触发，必须保留组件单元测试证据，不可填写“手动通过”。

## 五、多 Agent 归属与协作：人工测试（P0/P1）

### TEAM-01：清单显示成员归属（P0）
- **操作：** 创建 Host 团队对话，让 A、B 各自调用 `write_todos` 创建不同任务清单。
- **期望：** A 的清单标注 A，B 的标注 B，消息气泡不会混成同一 Agent；可在对应卡片编辑。
- **证据：** Host/A/B ID、两个独立 Todo 卡片截图。

### TEAM-02：A 清单定向回传 A（P0）
- **操作：** 修改 A 的清单并点击“同步给 A”。
- **期望：** 发送消息指明所属成员 A，并通过现有目标 Agent 路由/Host `ask_agent` 交付给 A；A 的清单实际更新。
- **注意：** 确认**真实工具调用**，不能仅以按钮文字断言已定向完成。

### TEAM-03：A 修改不覆盖 B（P0）
- **操作：** A 清单加一条任务，随后查看 B 的同一会话清单和任务工具轨迹。
- **期望：** B 的清单内容不受影响；Host 不把 A 的列表整体当成团队列表覆盖 B。

### TEAM-04：普通对话的目标 Agent 选择不回归（P0）
- **操作：** 单 Agent 聊天中按原有方式选择目标 Agent 后再同步 Todo。
- **期望：** 不被新的团队定向策略错误清空原有选择；可以按原有流程使用。

### TEAM-05：未知成员 / 退群后的编辑（P1）
- **操作：** 团队成员变更后刷新，再查看原历史清单的编辑入口。
- **期望：** 对无法确认仍属于团队的清单，不应盲目按旧成员 ID 派发；记录实际页面表现和后端响应。
- **说明：** 这是权限边界风险检查。当前阶段不能因 UI 禁用就宣称服务端权限已经完善。

### TEAM-06：切换会话与刷新（P1）
- **操作：** 团队会话 T1 出现 A/B 清单；再到 T2 编辑，返回 T1 并刷新。
- **期望：** 历史与清单正确关联各自会话；不串任务、不串 Agent。

### TEAM-07：阻塞和失败（P1）
- **操作：** 让 A 执行一个受控失败任务（例如不存在的测试文件），Host 汇报结果。
- **期望：** 页面不能仅凭一段模型总结将任务认定为成功；保留失败/阻塞信息，若存在 Run 应关联真实记录。

### TEAM-08：完整的团队共享任务分配（未来 P2，当前 N/A）
- **操作（未来）：** Host 生成带 `task_id`、`depends_on`、`assignee_agent_id` 的团队总计划，再做分派、依赖释放、并发冲突验证。
- **期望（未来）：** 后端版本冲突拒绝、独立任务证据、可靠状态同步。
- **当前状态：** **N/A：统一团队任务存储/依赖调度尚未实现。**

## 七、用户可直接复制的三段测试提示词

**提示词 A（单 Agent）**

> 我们测试 Octop 的 Todo 双向交互。请用 write_todos 创建四个任务：检查 API、修改功能、增加测试、运行回归。每一步先报告状态，完成验证后才标记 completed。不要实际修改生产代码。

**提示词 B（多 Agent）**

> 请让团队中的前端 Agent 和测试 Agent 各自创建独立 Todo。前端负责页面交互，测试负责测试用例。通过 ask_agent 分派工作；请告诉我每份清单属于哪个 Agent，不要把两个成员的任务合并成同一份个人清单。不要操作生产环境。

**提示词 C（错误处理）**

> 请在测试工作区执行一个不会影响生产的失败验证，比如检查一个确定不存在的测试文件。遇到错误后必须说明失败、保留待办任务，并给出下一步建议。不能把失败任务标记 completed。

## 九、放行标准与回退

- **P1 纯函数模块的最低放行门禁：** CTX-01～09 全部通过，`ruff` / `mypy` 通过；没有破坏现有 Agent 对话功能。
- **Todo 单 Agent 与团队定向同步的最低放行门禁：** TODO-01～05、TEAM-01～04 的可执行用例通过，并至少记录一次带真实工具轨迹的端到端样本；只跑前端测试不能代替这一步。
- **不放行的情况：** 跨账号/跨成员读取或覆盖、丢失未完成任务、虚报完成、过期草稿静默覆盖、泄露原始敏感 payload。
- **未完成项：** CTX-10、TEAM-08 等按 `N/A` 留待后续 P1/P2，不应因未实现而填写通过。
- **回退：** 若新代码影响运行，定位问题提交并在 `dev` 上修复或安全回滚；不自动操作 `main`。保留失败日志与测试证据。

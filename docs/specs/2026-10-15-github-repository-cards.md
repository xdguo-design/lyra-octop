# 创作页 GitHub 仓库卡片设计

## 目标与边界

允许用户在「创作」页手动登记 GitHub 仓库，作为独立的代码仓库卡片查看和打开。第一版只保存仓库名称、说明、URL 和文件夹归属；不授权 GitHub、不拉取仓库元数据，也不克隆或操作代码。

## 方案选择

1. 复用现有服务条目与 URL 字段，通过 GitHub 主机识别仓库卡片。无需数据库迁移，可沿用现有 CRUD、账号隔离和文件夹管理。**采用此方案。**
2. 新增持久化的 `github` 条目类型。数据语义更明确，但需要扩展数据库约束和 SQLite/PostgreSQL 迁移，对当前仅需登记链接的场景复杂度过高。
3. GitHub OAuth 同步仓库列表。可自动呈现私有与公开仓库资料，但需要授权和权限范围设计，超出本次手动登记范围。

## 交互与数据流

- 在「创作」页增加「添加 GitHub 项目」入口，复用现有条目表单，填写名称、说明、仓库 URL 和文件夹。
- URL 必须是 `https://github.com/{owner}/{repo}` 形式，可有一个末尾斜线；不接受 `www` 主机、`.git` 后缀、查询参数、片段或额外路径。保存时仍走现有服务条目 API。
- 仓库分类完全由规范化 URL 决定：主机为 `github.com` 且路径恰好包含 owner、repo 两段时出现在新增的「代码仓库」筛选项；其他服务显示在「应用」筛选项。编辑 URL 后分类随之变化。
- GitHub 表单在提交前校验上述 URL 格式。现有后端服务 API 继续执行通用 http/https、host 与无凭证校验；因为数据仍是通用服务条目，后端不区分它是否来自 GitHub 表单。
- 仓库卡片使用 Lucide GitHub 图标，不抓取或显示仓库截图；展示名称、说明和链接，点击卡片在新标签页打开。保留现有复制链接、移动文件夹、编辑和删除能力。
- 编辑已有条目时保留名称、说明、URL 和文件夹；分类由当前 URL 重新计算。删除按现有确认流程执行。

## 边界与失败处理

- URL 在 GitHub 表单中限制为上述仓库地址；后端通用 URL 校验不得允许非 http/https scheme、无 hostname 或带用户名/密码的 URL。
- 不访问仓库 API，不保存访问令牌。私有仓库可保存链接，但查看权限由用户已有的 GitHub 会话决定。
- 不满足仓库地址格式时，GitHub 表单阻止保存并显示校验错误；普通服务仍可填写任意符合现有后端校验规则的网址。
- 仓库资料变更不会自动同步到卡片；用户可编辑名称和说明。

## 验收与验证

- 可添加公开或私有仓库 URL；条目显示为代码仓库卡片，并在「代码仓库」筛选中出现。
- 点击卡片打开 GitHub 仓库新标签页；复制链接、移动文件夹、编辑和删除均沿用现有功能。
- 普通网站服务仍归入「应用」且不受 GitHub 卡片逻辑影响。
- 拒绝 `www.github.com`、非 GitHub 域名、缺 owner/repo、额外路径、`.git`、查询/片段和无效 URL；允许标准地址尾部有或没有 `/`。
- 编辑条目并修改 URL 时，仓库条目与普通服务条目会按新 URL 在「代码仓库」和「应用」筛选间切换；仓库卡片显示 GitHub 图标作为无截图预览时的固定视觉。
- 验证前端类型检查、创作页相关测试及后端现有 creations API 测试。

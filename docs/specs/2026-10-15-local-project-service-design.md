# 本地项目服务启动设计

## 目标与边界

在工作台项目菜单中启动一个已有的本地 Web 项目，给它分配本机端口，并提供状态、日志和停止操作。项目根目录只检查一层，不递归扫描子目录。项目根目录必须位于服务器配置的 `workbench_code_root` 范围内；服务运行在 Octop 主机上，只监听 `127.0.0.1`。第一版要求打开 Octop 的浏览器也运行在 Octop 主机上；远程浏览器访问和局域网访问不在范围内。

第一版支持从根目录标记识别 npm、Maven、Gradle 和 Java JAR。根据识别结果预填可编辑的启动命令；不负责创建、修改或下载项目文件，也不处理 Docker、局域网或公网访问。服务记录随账号项目保存，启动、停止操作仅限管理员，因为启动会在主机上执行项目代码。Octop 重启后记录保留，但进程不自动重启。

## 方案选择

1. 仅登记已经运行服务的网址：没有主机代码执行风险，但不能替用户启动服务。
2. 在项目菜单托管启动本地进程：可满足启动、端口分配、日志和停止需求；须限制项目路径和监听范围。**采用此方案。**
3. 为每个项目创建容器：隔离性更强，但依赖 Docker，增加运行和部署要求，不作为第一版范围。

## 交互与数据流

项目需关联一个位于 `workbench_code_root` 下的项目根目录，并将相对路径保存在项目记录中。项目菜单沿用现有下拉菜单样式，显示“查看代码”和“启动本地服务”；运行中显示状态、访问地址、日志和停止操作。启动流程只检查该目录的直接子项：`package.json`、`pom.xml`、Gradle 文件和顶层 JAR。命令由“可执行程序”及“参数列表”两个字段组成，参数逐项编辑；不把命令行文本交给 shell 解析。分配端口以 `{port}` 参数占位符注入；框架默认建议同时绑定 `127.0.0.1`。启动器选取空闲端口，启动子进程并探测监听状态。项目目录和命令通过账号项目 API 持久化；分配端口、运行状态、进程句柄和有界日志仅保存在运行时服务管理器中。

## 边界与失败处理

- 将解析后的项目路径限制在配置根目录内，拒绝路径穿越与符号链接逃逸；根目录扫描只读直接子项。
- 启动命令使用参数数组执行，不经 shell 展开；管理员启动前显示将执行的程序、参数和项目目录。
- 端口冲突时重新分配；进程退出、启动超时或未监听时标记失败并保留有限日志供排查。
- 停止时终止项目的整个子进程树；Octop 正常关闭时也清理其托管的进程。
- 未知项目由管理员编辑启动命令；无法安全解析或无法监听本机端口时不显示为运行成功。

## 验收与验证

- 根目录中的 npm、Maven、Gradle、JAR 标记可给出相应启动建议；只有子目录存在标记时不自动识别。
- 菜单可创建、启动、查看日志、停止服务；保存后重载页面仍显示项目配置，Octop 重启后服务保持停止。
- 端口仅能通过 Octop 主机本机访问；其他用户不能启动或停止该主机进程。
- 本机浏览器可打开分配的 `127.0.0.1` 地址；从其他设备打开 Octop 的用户不会获得可用的服务链接。
- 验证路径越界、符号链接、端口冲突、启动命令失败、启动超时和子进程清理等边界。

# 首页模型思考模式设计

## 目标

在首页 `/home` 的模型下拉菜单中，让用户能为支持推理设置的模型选择思考模式。复用现有模型能力描述、用户偏好和线程字段；不改变模型提供方配置，也不新增后端 API。

## 方案与选择

1. **模型项内的思考入口（采用）**：只对有 `reasoning_config` 的模型显示思考入口，打开后设置模式，并在模型提供强度选项时显示强度。
2. **模型选择器旁的全局开关**：入口更显眼，但“自动”模型可能解析成不同模型，开关作用对象不明确。

采用方案 1，与 `/chat` 现有按模型展示能力和思考选项的交互一致，也不会向不支持该能力的模型展示无效控件。

## 交互和数据流

- 首页模型菜单中的支持推理模型显示思考入口；不支持推理的模型不显示该入口。`自动`项不展示思考设置，因为它可能路由到不同模型。
- 模式选项为“自动 / 开启 / 关闭”。模型能力包含 `efforts` 时，另显示该模型提供的思考强度选项；其他模型不显示强度设置。
- 模型切换时，按现有规则选择该模型的用户级 `model_reasoning` 偏好；若无用户偏好，则使用模型能力中的默认模式和默认强度。
- 用户修改思考设置后，当前已有线程使用现成 PATCH 字段 `reasoning_mode` / `reasoning_effort` 保存。新线程创建后的首次 WebSocket 消息携带这两个字段，由现有服务端 turn 处理写入线程设置。
- 每次发送使用当前选中模型对应的思考模式和强度；既有后端能力解析决定最终供应商参数。不会改变 Agent 默认模型或全局模型配置。

## 变更边界

- 只改首页模型选择和发送接线，以及为必要状态补充局部单测。
- 复用 `ResolvedModel.reasoning_config`、`preferences.model_reasoning`、线程 PATCH 字段和 `useChat` 现有可选参数。
- 不抽取新的公共组件，不改 `/chat`，不新增迁移、接口、依赖或设置页。

## 验收与失败场景

- 支持切换推理模式的模型显示入口；无推理能力或 `status_only` 的模型不出现可切换选项；强度只列出模型声明的值。
- 选好设置后发送：新线程的首条消息带上模式/强度；已有线程切换设置后刷新仍保留。
- 从有不同默认设置的模型间切换时，不串用另一个模型的模式/强度。
- 能力元数据缺失时不显示入口并沿用服务端默认行为；线程保存失败时显示设置保存错误，不静默宣称已持久化。
- 定向验证首页对应单测及 `cd dashboard && npx tsc -b`；避免运行会格式化无关未提交文件的全量 `make all`。

## 假设

- “思考的那个”指按模型能力配置推理模式，与 `/chat` 现有设置语义相同。
- 用户级偏好只作为默认值；选择值保存在当前线程，符合平台现有 Chat 行为。

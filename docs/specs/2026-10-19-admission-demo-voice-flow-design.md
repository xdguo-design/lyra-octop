# 入院 Demo 语音转写与 AI 流程设计

## 目标与范围

调整住院登记 Demo 底部语音区：语音识别成功后不打开人工输入弹窗；转写文字显示在录音区下方；身份识别和入院安排确认后，识别结果自动交给现有 AI 提取登记字段。只改 Dashboard 页面交互，不新增 API、数据表或语音供应商。

沿用既有隐私边界：身份识别和入院确认之前，识别文字只留在当前页面，不发送给 AI。此 Demo 继续使用虚构登记数据，不接真实 HIS。

## 方案比较

1. **转写内联显示，确认后自动提取（采用）**：复用 `/api/admission-demo/extract`，将最终识别文本直接传给现有 `sendMessage(text)`；此前阶段仅显示文本。满足无弹窗和直接 AI 处理，同时保留现有身份/入院确认门槛。
2. **所有阶段都自动发送 AI**：可以更早回答语音，但会把确认前的联系人等内容送给模型，违反现有隐私约束。
3. **保留转写弹窗等待手动提交**：保留人工确认，但不符合用户要求的语音成功后直接进入 AI 流程。

## 页面与数据流

- `useVoiceInput.onInterim` 仍更新临时转写；最终 `onText` 保存本轮已识别文本供页面显示。
- 识别成功后不设置 `manualInputOpen`。语音区下方显示最新一条转写；录音中显示现有收音波形和状态。识别成功的文本保留到下一轮识别或页面流程重置。
- 只有录音开始时和最终识别回调时都处于 `stage === "details"`，才将最终转写传入现有 `sendMessage(text)` 并请求提取接口；保持 `pending` 防重复提交，再将提取结果合并到表单。录音开始于更早阶段的文本只显示、不因页面后来进入 details 而补发。其他阶段只显示转写，不触发 AI。
- AI 提取失败时在语音区/页面状态中显示现有本地化失败提示，继续允许手动输入和重试；不因网络或模型失败清空转写。
- “手动输入”按钮仍可打开现有弹窗，手动提交行为不变。语音转写不调用弹窗。
- 不保存音频或原始转写到服务器；AI 请求仍只在确认后的信息补充阶段发送。

## 原型语音面板布局

- 底栏占满原型主内容宽度，包含返回流程首页、居中的语音面板和人工帮助入口；语音面板内部采用麦克风、状态文案、音量波形、计时和结束录音按钮的横向排列。
- 点击结束录音后，转写在语音面板下方显示；录音时到达的临时文本也显示在同一行。浏览器原生识别没有音量数据时只显示状态和转写，不绘制波形。
- 计时只在录音状态显示并从 `00:00` 开始；结束录音调用现有停止入口。快速指令和隐私说明保持在语音面板下方。

## 失败场景与验证

- **身份未确认时说出联系人或电话**：转写可见，提取 API 不被调用。
- **识别结束时模型请求失败或返回空字段**：保留本轮转写，显示可理解的本地化错误/空结果反馈，不打开弹窗；用户可以再次说或手动修改。
- **录音期间页面阶段改变**：是否可自动发送同时检查录音开始阶段和最终回调阶段；在 identity/application 阶段启动的录音不会因随后进入 details 而发送。AI 请求由现有 `pending` 防重。
- **用户重置流程**：清空转写和错误状态，与现有 `restart()` 清理保持一致。

定向 Dashboard 测试覆盖：确认前只显示转写且不调 AI；确认后识别成功自动调 AI、文本保留在语音区、成功不打开 Modal；AI 失败显示反馈并保留文本；手动输入弹窗仍可用。随后运行 Admission Demo 页面测试、TypeScript、ESLint、Prettier 和生产构建。真实麦克风/云端识别仍需在页面授权后试音。

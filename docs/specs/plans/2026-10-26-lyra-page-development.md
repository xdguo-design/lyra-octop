## 1. 问题拆解

### 核心目标

把 V2.2 的 19 项逐页说明转成真实产品中的页面验收与开发顺序，并避免将演示原型数据、未接通执行器或 P2 概念误报为产品能力。

### 硬性约束

- `/tasks` 表示定时计划；`/runs` 表示持久运行记录，两者不得合并成一个语义。
- `created → cancelled` 表示尚未启动的运行直接取消；运行中的取消请求先显示 `cancel_requested`，仅以后端确认的终态显示 `cancelled`。
- HITL 沿用 `/chat` 现有确认卡，不新增 `/chat-approval`。
- Agent 编辑继续使用 `/experts` 内的抽屉，不新增 `/experts/:id`。
- 运行记录、知识处理、连接器授权、审批状态必须以服务端返回为准；不得展示假成功或假进度。
- 项目详情、应用目录和系统总览不能因原型图存在而自动成为已批准范围。
- 只触碰所选页面和直接相关测试；不格式化或清理其他工作区改动。

### 假设

- V2.2 是产品范围和状态语义来源，不是要求照搬静态 HTML 的开发指令。
- 当前本地代码和 API 才是实现事实；远程 `dev` 与本地工作区可能不同。
- V2.2 文档提到的独立 HTML、Playwright 安全回归脚本未作为可访问输入提供；因此产品代码的安全验证需使用仓库内测试，不能声称已重跑原型脚本。

### 主要失败模式

| 失败 | 防护与验收 |
|---|---|
| 页面凭演示数据显示已连接、已索引或执行成功 | API 缺字段/错误时展示未知、空或错误态；集成测试检查来源字段与错误分支 |
| 用户内容进入 HTML 注入上下文 | React 文本节点/安全 Markdown 渲染；用 `<img onerror>`、`<svg onload>` 输入验证无执行和无注入节点 |
| 越权查看项目、运行、文件或审批 | API owner/角色校验；跨用户集成测试验证 404/403 且无副作用 |
| `cancel_requested` 被误报为执行器已停止 | UI 直接呈现服务端状态；确认 created 与 running 两种分支 |
| 原型新增对象超出已确认范围 | 第 06 项须先确认对象/共享权限/回退行为；第 18、19 项保持延期 |

## 2. 方案比较与选型

| 方案 | 收益 | 风险/代价 |
|---|---|---|
| 逐页整体重做 19 张原型 | 表面一致、可以一次展示 | 会覆盖已有功能、混淆原型数据和 API 能力，并把 P2 概念误纳入范围 |
| 按 V2.2 的页面分类逐项核验，只开发可执行缺口 | 保留现有交互与后端合同，工作可独立验证 | 视觉统一与移动端需跨页面分批完成 |

**选型：** 采用第二种。已满足描述的页面只做差距核验，不为“有 19 张图”而重写；有明确合同的缺口按优先级开发；不明确的新增范围先停在决策门。

### 2026-10-27 用户确认扩展范围

用户明确将项目详情、应用目录和系统管理总览纳入本次开发。以现有服务端契约作为数据和权限来源，缺少契约的成员管理、安装和聚合状态不使用模拟数据。

- [x] 应用目录：显示内置路由和个人应用，支持搜索、失败重试及跳转现有管理入口，不将模拟适配器标记为真实应用。
- [x] 管理总览：管理员入口展示健康接口字段，链接用户、模型、存储、安全、审计和设置页面；覆盖未授权访问及导航。
- [x] 对新增页面、路由、国际化和权限执行定向测试、TypeScript 检查和生产构建；桌面与手机视口已走查。最终结果见下方验收记录。

每个页面工作包至少验证以下边界：

1. **注入：** 在项目名、工具描述、错误文本、聊天内容等用户可控文本中输入 `<img src=x onerror="window.__pwned=1"><svg onload="window.__pwned=2"></svg>`；断言其只作为文本显示、没有注入 DOM 元素且事件未触发。
2. **越权：** 使用第二个用户访问第一用户的项目、文件、Run、审批和连接器资源；断言 API 返回 404/403、UI 不展示私有字段、不发生写操作。
3. **状态竞态：** 延迟旧列表/详情请求后切换项目或页面；旧响应不得覆盖当前对象。重复提交、取消和刷新均以服务端返回为准。
4. **数据暴露：** 断言 API 不返回页面不需要的原始提示词、凭据、完整 payload 或未脱敏异常；前端不渲染原始 JSON。

## 目标与约束

目标是把 Octop 的对话能力做到可验证地覆盖用户所需的 ChatGPT 工作流，并吸收 Grok Bot / 社区替代项目中适合自托管多 Agent 产品的交互模式。不是逐项仿制界面，也不把不同服务的所有能力无差别塞进一个版本。

- Octop 是自托管、多用户平台；文件、凭据、任务和 Agent 必须继续遵循现有用户/Agent 隔离。
- 复用现有 Skills、memory、cron、Agent Teams、HITL、桌面远程控制、MCP connectors、文件解析和工作区能力。
- 新持久任务只有在需要跨进程恢复、重试或调度时才引入持久队列；不因参照项目使用容器而默认增加服务。
- 对外动作、文件写入、浏览器登录和 Agent 间委派需要可见授权、审计和资源预算。
- “达到 ChatGPT 功能”按用户可见任务闭环和可靠性验收，不声称与其专有模型或订阅能力完全等价。

## 参照能力

ChatGPT 官方能力概览列出联网搜索与 Deep Research、图片理解/生成、文件与音频上传、数据分析、语音、Canvas、Memory、Projects、Scheduled Tasks、自定义 GPT 等功能；实际开放情况随计划、设置和平台而变。Octop 本轮应优先对齐常见对话工作流：附件理解与引用、联网研究、数据分析、长期项目上下文、语音和可恢复任务。

OpenGrokBot 是与 Grok Bot 无官方关系的社区自托管替代项目，不是 xAI 源码。其公开项目重点包括每位 Teammate 独立电脑与工作区、可接管浏览器、可见记忆变更、外部动作审批、持久 routine、Agent 间受限委派、群组派工、每日额度和移动通知方向。它可作为产品形态参考，不能当作 Grok 官方能力规格。

## 分阶段路线与进度分布

进度是规划拆分比例，不是已完成百分比；每一阶段完成后都要按验收条件更新。

| 阶段 | 工作范围 | 计划占比 | 当前状态 | 主要验收 |
|---|---|---:|---|---|
| A. 对话可靠性基线 | 本轮五项代码问题：pytest 收集、解析段完整性、扫描 PDF 状态、同 revision 并发幂等、创建页契约 | 15% | 定向回归完成；全量非 live 套件未完成 | 全量套件通过或逐项归因基线失败；目标前端类型检查通过 |
| B. 文件工作流闭环 | 从现有文件切片计划推进 OCR/部分状态、按需读取与搜索、引用定位、预览、编辑冲突、Office 生成及导出 | 30% | 现有读取/搜索首切片已交付；本轮补 workspace 版本写保护和缓存 SHA-256 复核；OCR/引用/编辑/导出仍未完成 | 规格 AC 在 Home 与 Chat 均通过；重启/重复请求/恶意文件测试；引用能定位到页/行/cell/slide |
| C. 对话工具能力 | 联网搜索与带来源研究、CSV/XLSX 安全分析/图表、图片/音频输入与结果呈现；工具使用前后状态及失败原因可见 | 20% | 搜索来源首切片已交付；本轮修正超额图片状态；数据分析、音视频理解仍未完成 | 无工具/超时/限流/恶意提示词下正确降级；来源可核验；数据分析进程和资源受限 |
| D. Teammate 与自治任务 | 利用现有 Agent Teams/HITL/cron/远控，补持久任务、状态/停止/恢复、逐项审批、屏幕接管、限定方向的 handoff、群组结果汇总与额度 | 25% | 一次性 Cron 重启防重、Admission 过期数据清理，以及 Cron 持久运行历史/详情抽屉/同进程取消已交付；跨进程恢复/取消、受限委派、默认 browser Provider 与演示语音兼容仍待补 | 重启后状态明确且不自动重复外部动作；取消/审批边界可验证；越权 handoff、循环委派、任务资源耗尽被拦截 |
| E. 项目记忆与 routines | Projects 式聊天/文件/指令上下文；Memory 的可查看、编辑、清除；把示范或对话流程保存为有版本、可测试、可暂停的 routine | 10% | 基础 memory/skills/cron 已有；项目与 routine 产品闭环尚未完成 | 用户能审查修改内容；routine 沙箱/审批策略显式；删除与撤销生效 |

## 立即执行顺序

1. 完成本轮五项可靠性修复与回归，冻结并记录本次审查发现；不在此批次扩张新产品面。

3. 对 ChatGPT 常用工具建立 Octop 能力矩阵：能力、API/UI 入口、适用模型、数据边界、禁用/失败状态、自动化验收用例。
4. 对 Teammate 工作流先盘点 Octop 已有 Teams、审批、远控、cron 的真实边界；只补跨重启任务状态、受限委派和可见审批链等缺口。
5. 最后评估语音、移动通知、演示学习 routine。每项需有明确使用场景和资源/安全成本，再决定是否进入版本计划。

## 风险与防护

| 失败场景 | 防护要求 |
|---|---|
| 扫描件/超大文件被误报“完整阅读” | 解析覆盖率、OCR 缺失和限制范围需显式展示；模型上下文标记未读部分；默认不伪造引用 |
| 文件、网页或其他 Agent 内容注入工具指令 | 内容按不可信数据隔离；写入、发送、登录、委派等副作用经过策略检查和用户审批 |
| 同一任务重试或两个 worker 抢占导致重复操作 | 稳定任务 ID、幂等状态迁移、外部副作用前审批/去重；调度禁止同 routine 重叠运行 |
| Agent 循环互相委派或消耗失控 | 方向 allowlist、委派深度/调用数限制、单 Agent token/CPU/时长预算和紧急停止 |
| 浏览器登录凭据泄漏或跨 Agent 访问 | 独立工作区/profile、严格用户与 Agent 所有权校验、凭据不进入对话日志、审计敏感操作 |

## 验收矩阵要求

后续验证分为四层，不以单测通过代替产品闭环：

1. 单元/集成：解析边界、owner 隔离、状态迁移、幂等、重试、审批授权和数据限额。
2. UI/浏览器：Home 与 Chat 上传、状态呈现、引用跳转、工具确认、取消/重试、移动尺寸及键盘访问。
3. 提供商矩阵：支持的文本/视觉/音频模型能力显式声明；不支持的工具组合必须解释并降级。
4. 部署矩阵：Windows/Linux、SQLite/PostgreSQL、重启恢复、并发请求和无模型凭据模式；真实模型测试单列并受控。

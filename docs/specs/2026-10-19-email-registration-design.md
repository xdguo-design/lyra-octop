# 邮箱验证码注册设计

## 目标与范围

自助注册使用邮箱地址作为登录名：创建的 `username` 与规范化后的 `email` 完全相同。用户先验证邮箱，再设置密码并提交注册；账号状态仍为 `pending`，只有管理员在现有「用户」管理页批准后才可登录。注册者不再填写单独用户名。

管理员审批已有完整链路（`pending` 状态、登录拦截、管理员查看和批准/拒绝），本设计不新增第二套审批入口。用户记录已有 `email` 字段和邮箱唯一性约束。

## 方案比较

1. **邮箱直接作为 username（采用）**：`username=email`，登录、审计和管理界面均沿用现有用户名字段；不引入邮箱前缀映射或用户名冲突后缀。需要让自助注册接受完整邮箱长度，并将格式限制为可安全用于跨平台用户目录的邮箱字符集。
2. **邮箱登录、内部生成 username**：可以保留现有 64 字符 username 规则，但会产生用户看不见的第二身份，也可能遇到前缀冲突。用户已明确选择邮箱名就是用户名，因此不采用。

## 页面、接口与数据流

- 注册页将用户名输入替换为邮箱输入，加入“发送验证码”和验证码输入；保留显示名称、密码确认以及现有 CAPTCHA。发送邮件前必须通过 CAPTCHA。
- 增加公开的验证码发送接口。请求邮箱先规范化并校验；验证码使用密码学安全随机数生成，存储 HMAC 摘要而非明文，有效期 10 分钟，最多尝试 5 次；同一邮箱至少间隔 60 秒发送，并沿用现有每客户端 IP 每 10 分钟最多 5 次的注册限流。该限流在发送验证码时计数，最终注册提交不重复计数。邮箱冷却检查与验证码预留必须在数据库中原子完成，同一邮箱的并发请求最多一个能预留并发送验证码；只有 SMTP 成功后挑战才可用于注册。
- 在当前未发布的 schema v26 migration pair 中新增 SQLite / PostgreSQL 共用验证码表，保存规范化邮箱、摘要、过期时间、尝试次数、创建时间和发送成功时间。对邮箱维持单个挑战；冷却检查/预留通过条件 upsert 在单条数据库原子操作中完成，保留失败的 SMTP 预留以落实冷却，只有 SMTP 发送成功的记录才可验证。校验与消费必须原子执行，成功、过期或次数耗尽后均不可重放。过期记录在发码时清理，避免无效挑战长期积累。已记录为 v26 但缺少此表的数据库由幂等迁移补齐函数修复。
- 注册接口接受邮箱、密码、显示名称和邮箱验证码。验证码通过后消费一次，再调用现有 `register_public` 创建账号，设置 `username=email`、`email=email` 和 `status=pending`。已有数据库邮箱唯一约束负责并发重复注册保护。失败或重放不创建用户。
- SMTP 由服务进程环境变量配置：`OCTOP_SMTP_HOST`、`OCTOP_SMTP_PORT`、`OCTOP_SMTP_USERNAME`、`OCTOP_SMTP_PASSWORD`、`OCTOP_SMTP_FROM`。发信使用 STARTTLS，通过 `run_in_executor` 避免阻塞 async 请求；SMTP socket 连接、STARTTLS、认证和发送均须设置 10 秒有界超时，避免占满共享执行器。SMTP 凭据只从环境读取，不写入数据库、日志或 API 响应。另要求设置独立于数据库的 `OCTOP_EMAIL_CODE_SECRET`，值必须为恰好 64 个十六进制字符（32 个随机字节，可用 `secrets.token_hex(32)` 生成），使用它对邮箱、验证码做 HMAC；缺失、格式错误或长度不足时拒绝发码。不得复用 JWT 密钥，因为 JWT 密钥存储于数据库。SMTP 未配置、连接或发送失败时返回明确错误，不创建用户，并使本次验证码不能用于注册。
- `username` 当前 API 的 64 字符校验仅用于常规管理员创建用户；自助注册将验证邮箱并允许最多 254 字符。登录接口和用户名索引已可接受邮箱文本，无数据库 username 长度约束。邮箱格式需限制路径分隔符、Windows 保留路径字符及尾随点/空格，避免 `username` 用作用户目录名时越界或无法创建目录。
- 更新注册相关 API 文档、配置文档、前后端中英文文案和注册测试。现有管理员用户列表可直接显示邮箱形式的 username 与 email，无需审批 UI 改造。

## 安全与失败场景

- **验证码请求滥用或邮件轰炸**：验证码发送需先通过 CAPTCHA；按客户端 IP 沿用现有 5 次 / 10 分钟限流（仅在发送验证码时计数），并按规范化邮箱以数据库原子条件实施 60 秒发送间隔。超过限制不发送邮件；同邮箱并发请求只有一个能发送。
- **猜测、过期或重放验证码**：使用独立环境密钥比较 HMAC 摘要；错误次数上限 5；有效期 10 分钟；成功校验通过数据库条件更新/删除原子消费，并发重复提交最多一次成功。数据库备份泄露不包含 HMAC 密钥。
- **SMTP 失败、超时或请求并发**：每个阻塞 socket 操作最多等待 10 秒；超时异常会将挑战标记为不可验证并保留 60 秒邮箱冷却。并发请求不能创建另一挑战或发送第二封邮件。服务端仅记录不含验证码、密码和 SMTP 凭据的错误信息，用户冷却结束后可重发。
- **大小写/并发注册重复邮箱**：邮箱先 `strip().lower()`；用户表唯一约束作为最终并发裁决；已有账号不会因再次注册被覆盖。
- **恶意邮箱构造路径段或超长 username**：拒绝路径分隔符、Windows 非法文件名字符和不符合邮箱长度/基础格式的地址；覆盖 Windows 与 POSIX 路径用例。
- **恶意发送导致验证码表累积**：发码时删除过期挑战，再按邮箱写入当前记录；验证表只留有效挑战和近期活跃邮箱记录。

## 验证策略

- 后端单元/集成：有效验证码创建 `pending` 用户且 `username == email`；账号审批前登录失败，批准后可登录；错误、过期、超次、重放均不建用户；大小写规范化和重复邮箱；并发同码只有一次成功；同邮箱并发发码只发出一封邮件；SMTP 未配置、发送失败或 socket 操作超时均不建用户；HMAC 环境密钥缺失、格式错误或不足 32 字节时拒绝发码；IP 和邮箱限流。
- 数据库：SQLite 与 PostgreSQL schema v26 migration pair 建表及索引；已处于 v26 的数据库由幂等修复补齐；验证码消费条件对两个数据库方言一致。
- 前端：邮箱输入、CAPTCHA 后发送、倒计时/失败提示、验证码和密码校验、提交成功状态；中英文 locale key 保持一致。
- 定向验证后运行 `uv run pytest` 对应后端用例、Dashboard 对应 Vitest、`cd dashboard && npx tsc -b`、目标 Ruff / Prettier 检查；不运行会重写大量既有文件的 `make format-all`。

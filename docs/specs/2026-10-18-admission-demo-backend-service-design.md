# 住院登记 Demo 独立后台服务设计

## 目标与边界

为住院登记 Demo 增加一个独立进程运行的后台服务。服务接收语音识别后的文本字符串，先保守清理，再抽取到固定 JSON 字段，校验字段并保存草稿；用户明确确认后，将草稿标记为已提交并生成模拟回执。

服务与 Demo 同仓、同次部署，作为 Octop 安装的一部分运行。它复用 Octop 当前配置的活跃模型和控制面数据库，但单独监听内部端口；不作为脱离 Octop 的独立产品运行。Demo 前端继续使用同源 `/api`，由 Octop API 完成登录认证并转发到后台进程。后台进程仅监听 loopback/内部网络，并要求服务间凭据。

本功能只处理 Demo 当前的虚构申请。它不判断入院资格，不调用真实 HIS、医保、短信、打印或真实医院服务。原始音频和原始转写文本不持久化。

## 方案对比与选择

1. **独立进程，通过 Octop API 代理（采用）**：后台独立启动和监听内部端口；Octop API 校验登录用户后，使用服务间凭据转发用户 ID 和请求。Dashboard 保持同源请求，免去浏览器跨域及混合内容配置。后台读取共享 Octop 配置、活跃模型和数据库。
2. **独立进程，浏览器直接调用**：Dashboard 直连新端口，后台自行校验 Octop JWT。需要配置 CORS、HTTPS 端口和 JWT 校验，且扩展了浏览器可访问的网络面。
3. **Octop 主进程内服务模块**：复用现有运行时最简单，但不满足独立进程要求。

采用方案 1。Octop API 路由只承担认证、转发和响应映射；清理、抽取、校验及持久化规则属于入院后台服务。后台不得信任来自公开网络的用户 ID；只接受 loopback/内部请求及有效服务间凭据。

## 固定 JSON 合同

请求正文以 JSON 字符串承载识别文本，文本长度上限 2000 字符。首次处理创建草稿：

```json
{
  "application_id": "RY202610160018",
  "text": "我是王晓梅，患者的女儿，手机号 13800138000，住北京市朝阳区示例路 8 号。"
}
```

首次请求使用 `POST /api/admission-demo/drafts`。Dashboard 将返回的 `draft_id` 放入当前标签页 `sessionStorage`，刷新后通过 `GET /api/admission-demo/drafts/{draft_id}` 恢复草稿。后续语音轮次使用 `POST /api/admission-demo/drafts/{draft_id}/transcripts`，请求正文为 `{"expected_revision":1,"text":"本轮识别文本"}`。人工修订使用 `PUT /api/admission-demo/drafts/{draft_id}/fields`，提交使用 `POST /api/admission-demo/drafts/{draft_id}/submit`；修改请求都带 `expected_revision`，提交另需 `consent: true`。每次修改成功后服务递增并返回 `revision`；版本不匹配返回冲突，不覆盖已保存内容。已提交草稿的重复提交在确认所有权后直接返回首次回执，即使重试携带的是提交前版本也保持幂等。已提交状态为终态；除读取及重复提交外，文本更新和字段修改都返回冲突，不改变数据或回执。

返回值必须是 JSON 对象，不返回 Markdown 代码围栏。`fields` 固定包含下列 6 个字符串键，顺序按登记表排列；缺失值用空字符串，不使用 `null`，不添加模型产生的其他键：

```json
{
  "draft_id": "01J...",
  "revision": 1,
  "status": "draft",
  "fields": {
    "contact_name": "王晓梅",
    "relationship": "女儿",
    "contact_phone": "13800138000",
    "address": "北京市朝阳区示例路 8 号",
    "emergency_contact": "",
    "emergency_phone": ""
  },
  "validation": {
    "valid": true,
    "missing_fields": ["emergency_contact", "emergency_phone"],
    "rejected_fields": {}
  }
}
```

键与现有登记界面的映射为：

| JSON 字段 | 登记含义 | 校验规则 |
|---|---|---|
| `contact_name` | 联系人姓名 | 非空时最多 40 字符 |
| `relationship` | 与患者关系 | 非空时最多 40 字符 |
| `contact_phone` | 联系电话 | 中国大陆手机号 `1[3-9]` 开头的 11 位数字 |
| `address` | 联系地址 | 非空时 5–200 字符 |
| `emergency_contact` | 紧急联系人 | 非空时最多 40 字符 |
| `emergency_phone` | 紧急联系电话 | 中国大陆手机号 `1[3-9]` 开头的 11 位数字 |

所有值先去除首尾空白，最大长度 200。含“或、或者、还是、or”等歧义表述的值不通过校验。提取出的手机号必须和本轮原始文本中的完整号码一致；不能用模型补全或猜测。字段缺失或无效时保留其空值/既有有效值，并在 `missing_fields` 或 `rejected_fields` 标明，要求用户确认或补录。`valid` 表示本轮候选字段无格式错误；草稿可以因必填字段未齐而仍处于不完整状态。

## 数据流与接口

1. Dashboard 将识别文本预填到输入框，用户提交后以 JSON 字符串发送到 Octop `/api/admission-demo` 路由。
2. Octop 校验 JWT 和用户状态，通过内部服务凭据转发已认证的 `user_id`、申请单 ID 及文本；JWT 本身不写入服务日志。
3. 后台清理转写文本：去除首尾空白、合并连续空白和明显重复标点；只在不改变实体信息时去除独立口头语/完全重复片段。姓名、数字、否定词、关系和不确定表达必须原样保留；无法安全清理时保留原文并让校验/模型抽取返回待确认项。
4. 后台调用 Octop 当前活跃模型，要求只输出上述 6 个键的 JSON 字符串值。严格 JSON 解析失败或模型超时，不将本轮候选值写入数据库。
5. 后台丢弃额外字段，对候选字段执行确定性校验，然后将有效候选与该用户的现有草稿合并并原子保存。返回固定字段 JSON 和校验结果，不回显或存储转写文本。
6. 手动修改的字段通过 JSON 请求保存到同一草稿。`PUT .../fields` 请求中的 `fields` 也必须包含完整六键，值全部为字符串；服务校验并保存有效值，拒绝额外键和非字符串值。最终提交请求包含明确同意标志；后台读取数据库里的草稿并再次验证所有必填字段，只有完整有效时才能改为 `submitted` 并生成模拟回执。重复提交返回相同回执，不生成第二条提交。

公开 API 保持在 Octop `/api` 下，供现有 Dashboard 请求器使用：创建、读取/恢复草稿、处理文本、保存手动字段、确认提交及放弃草稿。后台进程提供对应内部 API；内部 API 不由浏览器直接访问。所有读写按 `(user_id, draft_id)` 校验归属。用户重启登记时调用 `DELETE /api/admission-demo/drafts/{draft_id}` 删除本人未提交草稿，再清除当前标签页的 `draft_id`；已提交记录不能删除。最终提交成功后只清除当前标签页的 `draft_id`。历史草稿不能由其他用户枚举或读取。

## 持久化与组件

- 增加入院草稿 Repo 和数据库表，保存服务生成的公开 `draft_id`、`application_id`、整数 `user_id`、固定六字段 JSON、`draft/submitted` 状态、整数 `revision`、创建/更新时间及模拟回执 ID。数据库写入使用事务；所有修改携带 `expected_revision`，版本不匹配时返回冲突并保留较新记录。
- 不保存录音、原始转写文本、模型原始响应或登录令牌。日志只记请求 ID、阶段、失败类别和耗时，不包含字段值。
- 后台使用最小启动入口，不启动 Octop 的 Gateway、Cron 或 Agent 服务，避免两个进程重复执行平台后台任务。它使用现有 `ProviderStore` 从共享 provider repo 读取提供方配置，通过 `octop-harness` 的模型工厂创建模型；每次处理从共享 settings repo 读取当前活跃模型。不得另存一套 API 凭据或硬编码模型名。
- 配置后台监听地址、端口和服务间凭据；凭据只在服务端环境/本地配置中保存，不下发给 Dashboard。生产默认只监听 loopback/私网，不提供默认共享密钥。
- 数据库迁移按 SQLite 与 PostgreSQL 双方言提供。若实现时当前未发布的 v25 仍未发布，则把表定义并入 v25；否则新增下一迁移版本。

## 失败模式与处理

- **模型超时、不可用或返回非法 JSON**：返回可恢复服务错误，不保存本轮结果，草稿已有字段不变，用户可以手动输入。
- **歧义号码、冲突号码或不确定表述**：对应字段不自动写入，标记原因并要求用户确认。
- **内部服务不可达/凭据不匹配**：Octop API 返回服务不可用，不回退到浏览器端解析，不泄露内部地址或凭据。
- **用户篡改 draft ID 或访问他人草稿**：按用户 ID 检查归属，返回未授权错误，不读写数据。
- **并发语音/手动更新**：数据库更新使用事务和整数 `revision` 条件，冲突时要求重载草稿，不静默覆盖较新的人工修订。
- **重复最终提交或响应丢失后重试**：先校验草稿归属；若已提交，直接返回保存的首次回执，不再比较旧版本或重复执行状态转换。
- **已提交记录被后续请求修改**：提交是终态；读取和幂等提交外的所有写操作拒绝，保持字段与首次回执一致。
- **用户放弃未提交草稿**：只允许所有者删除 `draft` 状态记录；提交后不可删除。

## 验收与验证

- 后端单测：规范化边界、固定六键 JSON、非法/带围栏 JSON 拒绝、未知键丢弃、字段规则、号码来源匹配、歧义文本、模型超时。
- API 集成测试：未登录拒绝、JSON 长度限制、草稿写入/更新/读取归属、他人 draft 隔离、手动字段保存、提交时二次校验、提交响应丢失后的旧版本重试、已提交后写入拒绝、未提交草稿放弃/删除、内部服务鉴权及不可用处理。
- 前端测试：识别文本按 JSON 字符串提交；结果字段和页面表单一一对应；缺项/无效项可见并能手动修正；最终确认后才显示提交结果。
- 部署验证：独立服务可启动、健康检查可用；Octop API 到内部端口链路可用；SQLite 和 PostgreSQL 迁移均可应用；日志和响应中无原始转写或凭据。

## 不在范围内

本次不连接真实 HIS，不存储音频或完整原始转写，不做医学判断、医保校验、患者资格判断，不增加短信/打印能力，不为生产医疗信息系统制定留存或加密合规标准。

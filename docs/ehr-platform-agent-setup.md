# 在 Octop 中使用 HIS 证据驱动研发

Octop 已有“项目指令/知识库快照”和 Agent Run；`ehr-platform-developer` 专家把本项目的证据、PRD 与交付规则封装为可复用的 Agent 模板。此模板先存在于源码中；需要构建并重启/部署包含此改动的 Octop 版本后，才会出现在 `/experts`。

## 一次性配置

1. 在 `/experts` 新建 Agent 时选择 **HIS 证据驱动研发工程师**。
2. 建立或导入 `ehr-platform` Workbench 项目，绑定该 Agent 常用的 HIS 知识库。知识库应包含评审中的门诊收费 PRD、对应交互原型、目标院区 020 证据、003/020 差异表、服务 OpenAPI/事件契约和业务决议；文件必须保留版本与来源。
3. 在项目指令中记录 PRD 与证据文件的可访问路径、当前 PRD 版本、批准状态、需求 Owner、目标分支和服务仓库边界。不要把“评审中”写成“已批准”。
4. 之后从该项目启动一个 Run，选择专家的“从已确认需求开始开发”快捷提示，明确本轮需求 ID 和验收目标。每个 Run 固定其项目指令/知识库版本，结果可回看。

## 项目指令建议

```text
本项目是 ehr-platform HIS。先遵守仓库 AGENTS.md、memory.md（若存在）、服务 README 与契约 Owner 边界。
收费目标院区以现行 020 为业务事实基线；003/020 冲突逐项待决。PRD Q-01..Q-12 未关闭项不得由 Agent 推断。
真实医保、支付、票据接口未取得正式契约与联调环境前保持 TODO / 未完成，不得模拟成功。
每轮只交付一个已确认纵向切片，并保持 PRD → 原型 → 前端 → 应用/领域 → 契约 → 测试追溯一致；实现后将真实交互同步回原型。
只修改当前项目隔离工作树内的内容，保留已有脏改动；不得自动 push、合并或部署。
若平台没有该项目的代码写入/验证能力，停止声称已实现，报告具体阻塞。
```

## 当前能力边界

Octop 的 `/workbench/projects/{id}/code` 接口目前只提供目录和文件读取。WorkBench 代码查看器不是可写仓库；Run 会捕获项目指令、知识库和输入文件 revision，但该快照本身不会授予代码仓库读写权限。专家模板能规范分析和产出，不能越过这一权限边界。

要让 Agent 真正修改 HIS 源码，平台还需交付项目级隔离工作树能力：每个 Run 在用户拥有的项目副本/分支内编辑；路径限制在仓库根目录；记录前后 revision 与统一 diff；构建/测试在资源受限的隔离执行环境内运行；Run 终态保留差异和命令结果；push、合并、部署继续由人审阅触发。未实现这条链前，Octop 不能承诺自动改写目标 Git 仓库。
